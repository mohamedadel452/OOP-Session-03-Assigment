1) الـ Dispatch: إزاي الـ Runtime يعرف يشغّل أنهي دالة؟

الفكرة: الـ Compiler مش دايماً يعرف وقت الترجمة الدالة اللي هتتنفذ. لو النوع الفعلي مش معروف، القرار بيتأجل للـ Runtime.

الدوال العادية و virtual

  • دالة عادية: العنوان معروف وقت الـ JIT. نداء مباشر.
  • دالة virtual: الـ object فيه header بيشاور على الـ MethodTable بتاع نوعه الفعلي. الدالة ليها رقم slot ثابت، فالـ Runtime بيجيب العنوان من MethodTable[slot]. الـ override بيحط كوده في نفس الـ slot اللي في الأب.
  • تكلفتها: قراءتين من الميموري ونداء غير مباشر. ومعاها بيصعب على الـ JIT يعمل inlining.

الـ Interface مختلف

الـ interface slot مش ثابت لأن الـ class الواحد ينفذ interfaces كتير، وكل class بيرتبهم بشكل مختلف. فالـ CLR بيستخدم Virtual Stub Dispatch: عند كل call site بيتولد stub صغير بيخزّن نتيجة آخر نوع شافه (cache)، فلو النوع ثابت يبقى النداء سريع، ولو بيتغير يبقى أبطأ شوية. الـ .NET الحديثة بتضيف Guarded Devirtualization بالـ PGO: لو لقى إن النوع الغالب واحد، بيحط check ونداء مباشر.

مفهوم خاطئ: "الـ interface أبطأ بكتير من الـ abstract class". الفرق موجود لكنه صغير ومعظم الوقت مش هو عنق الزجاجة. المشكلة الحقيقية الأكبر هي الـ boxing مع الـ structs وكتر الـ allocations، مش الـ dispatch.

إيه اللي يساعد الـ JIT؟

public sealed class SqlOrderRepository : IOrderRepository { ... }
// sealed: الـ JIT يعرف إن مفيش ابن، فيقدر يعمل devirtualize
// لما يكون النوع معروف من الـ new أو الـ field المحدد

اتأكد بنفسك: افتح SharpLab.io واختار IL، وشوف الفرق بين call و callvirt في الأسطر القادمة.

2) virtual و abstract و override و new

class A {
    public virtual void F() => Console.WriteLine("A.F");
    public void G()          => Console.WriteLine("A.G");
}
class B : A {
    public override void F() => Console.WriteLine("B.F");   // نفس الـ slot
    public new void G()      => Console.WriteLine("B.G");   // دالة تانية بنفس الاسم
}

A x = new B();
x.F();        // B.F  : decided at runtime
x.G();        // A.G  : decided at compile time by reference type
((B)x).G();   // B.G
الكلمةبتعمل إيه في الـ ILالقرار بيتاخد
virtualدالة بـ slot جديد (virtual newslot)Runtime
abstractvirtual من غير جسم، والـ class لازم يبقى abstractRuntime
overrideبتعيد استخدام slot الأبRuntime
new (hiding)دالة جديدة مالهاش علاقة بالـ slot القديمCompile time، حسب نوع الـ reference
من غير أي كلمةنفس سلوك new مع تحذير CS0114Compile time

باگ في الإنتاج: نسيان override على دالة موجودة في الأب كـ virtual بيطلّع تحذير بس، مش error. الكود بيتبني، وبعدين الـ polymorphism يتكسر بصمت وتتنفذ دالة الأب. اعمل <TreatWarningsAsErrors> لتحذيرات زي CS0114 و CS0108.

ليه C# بتخلي virtual صريحة (عكس Java)؟ لأن الـ virtual dispatch بيمنع الـ inlining ومعمول عليه عقد: لازم الأب يتوقع إن حد يغير سلوك الدالة. جعلها اختيار واعي بيحمي من الـ Fragile Base Class.

3) Template Method مقابل Composition over Inheritance

Template Method: الوراثة لما تكون مناسبة

public abstract class ReportJob
{
    public async Task RunAsync()               // الخوارزمية ثابتة ومش virtual
    {
        var rows = await LoadAsync();          // خطوة متغيرة
        var text = Format(rows);               // خطوة متغيرة
        Console.WriteLine(Header() + text);    // خطوة اختيارية
    }
    protected abstract Task<IReadOnlyList<string>> LoadAsync();
    protected abstract string Format(IReadOnlyList<string> rows);
    protected virtual string Header() => "Report\n";
}

الأب بيتحكم في الترتيب، والأبناء بيملوا الخطوات. مناسب لما الـ skeleton ثابت فعلاً ومحدش هيغيره.

مشكلة الوراثة: Fragile Base Class

class Bag {
    protected readonly List<int> items = new();
    public virtual void Add(int x) => items.Add(x);
    public virtual void AddRange(IEnumerable<int> xs) { foreach (var x in xs) Add(x); }
}
class CountingBag : Bag {
    public int Added;
    public override void Add(int x) { Added++; base.Add(x); }
    public override void AddRange(IEnumerable<int> xs) { Added += xs.Count(); base.AddRange(xs); }
}
var b = new CountingBag();
b.AddRange(new[] { 1, 2, 3 });
Console.WriteLine(b.Added);   // 6 !  المفروض 3

الابن اعتمد على تفصيلة داخلية (إن AddRange بتنادي Add). لو الأب غيّرها، الابن يتكسر من غير ما حد يلمسه. الوراثة بتكشف التنفيذ الداخلي للأب.

Composition: الحل

public interface IPaymentGateway { Task ChargeAsync(decimal amount); }
public interface INotifier       { Task SendAsync(string msg); }

public class CheckoutService(IPaymentGateway gateway, INotifier notifier)
{
    public async Task CheckoutAsync(decimal total)
    {
        await gateway.ChargeAsync(total);
        await notifier.SendAsync($"Charged {total}");
    }
}

بدل CheckoutService : EmailSender : PaymentBase، بتركّب السلوك من أجزاء بتتبدل وقت الـ Runtime وبتتعمل لها mocks.

الحدود: الـ composition بتزود الـ boilerplate والـ indirection، ولو محتاج تعدّل كل سلوك الأب فعلاً فالوراثة أنضف. القاعدة العملية: وراثة لـ is-a حقيقية ومستقرة (والأب مصمم للوراثة)، وغير كده composition. وعلّم الـ classes اللي مش مصممة للوراثة بـ sealed.

4) DIP و ISP و الـ DI

ISP: Interface Segregation

// سيء: interface كبير
public interface IRepository<T> { T Get(int id); void Add(T e); void Update(T e); void Delete(int id); }

// أفضل: قدرات منفصلة
public interface IReader<T> { T Get(int id); }
public interface IWriter<T> { void Add(T e); void Update(T e); void Delete(int id); }

public class ReportService(IReader<Order> orders) { }   // مش محتاج Delete أصلاً

الـ client مايتجبرش يعتمد على دوال مش بيستخدمها. ده بيقلل الـ mocking المعقد وأثر أي تغيير.

DIP: Dependency Inversion

الـ high-level (منطق الأعمال) مايعتمدش على الـ low-level (EF Core أو SMTP). الاتنين يعتمدوا على abstraction، والـ abstraction يتعرّف جنب المستهلك مش جنب التنفيذ.

مفهوم خاطئ شائع: "الـ DI container = DIP". لا. الـ DIP مبدأ تصميم (مين يملك الـ interface). والـ DI تقنية لتمرير الـ dependencies. تقدر تستخدم container وتكسر الـ DIP لو الـ interface معرّف جوه طبقة الـ Infrastructure.

التسجيل في ASP.NET Core

builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();
builder.Services.AddSingleton<ReportCache>();

public class ReportCache(IOrderRepository repo) { }   // singleton بيعتمد على scoped!

باگ حقيقي: Captive Dependency. الـ singleton بيمسك نسخة scoped (وبالتالي DbContext) طول عمر التطبيق، فتتشارك بين الـ requests وتبوظ الـ thread safety والـ change tracking. في بيئة Development الـ framework بيرمي exception لأن ValidateScopes شغال، لكن مش مضمون إنك تشوفه في الإنتاج. القاعدة: الأطول عمراً ماياخدش الأقصر عمراً.

Lifetimeالاستخدامالخطر
Transientخدمات خفيفة من غير stateallocation كتير لو اتكررت
Scopedrequest واحد (DbContext)مايتحقنش في singleton
Singletoncache و config، لازم thread-safestate مشترك وتسريب ذاكرة

تكلفة الإفراط: عمل interface لكل class بتنفيذ واحد بيزود الملفات من غير فايدة. استخدم interface لما يكون في أكتر من تنفيذ محتمل، أو حد خارجي (HTTP, DB, ساعة النظام) محتاج تعزله في الاختبار.

Service Locator (Anti-pattern)

var repo = provider.GetRequiredService<IOrderRepository>();  // جوه الدالة

بيخبي الـ dependencies جوه الكود فمبتبانش في الـ constructor، ومبتتكتشفش إلا وقت التنفيذ. استخدم constructor injection.

مؤجل للجولة الجاية بسبب الحجم: تفاصيل الـ IL لكل حالة، و OCP و LSP و SRP، و Decorator مع الـ DI. اطلب أي واحد وهكمله.
